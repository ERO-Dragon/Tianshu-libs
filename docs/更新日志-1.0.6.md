# Tianshu Libs 1.0.6 更新日志

本文记录本次 libs 侧围绕 JJML 元数据能力、Gemma 分体 MTP、上下文预算和 thinking/COT 输出所做的接口与实现更新。

本日志按当前 staged 区改动整理，即 `HEAD -> index` 的 libs/common/docs/gradle 配置差异；不包含未暂存的 neoforge `.eclipse` 启动配置文件。

## 版本信息

- libs 版本：`1.0.6`
- JJML 版本：`2.1.2.0025-02b5d02`
- 主要目标：补齐上层需要的底层健壮能力，同时保持接口薄、职责清晰、避免业务语义进入 libs。

## 上下文预算与加载前规划

新增加载前 ctx 规划能力：

- `JavaLlamaServer.Builder.dryRunContextBudget()`
- `JavaLlamaServer.dryRunContextBudget(ServerConfig config)`
- `LlmContextBudgetPolicy`
- `LlmContextBudgetPlan`

设计语义：

- `dryRunContextBudget()` 在模型正式加载前调用 JJML context plan / 元数据 / 显存预算能力，用于推导建议加载的 `plannedContextSize`。
- 上层应把 `plannedContextSize` 显式写回 `contextSize(...)` 再启动服务。
- `start()` 会对同一组模型级参数再做一次校验；如果请求的 ctx 超出规划可接受值，启动失败并提示上层先使用 dryrun 结果。
- libs 不在 `start()` 中静默裁剪 `contextSize`，避免上层误以为加载的是请求 ctx。
- `getContextBudgetPlan(lane)` 返回启动阶段保存的 CHAT / TASK lane 计划，定位为运行期观测，不是加载后的补救入口。

相关字段语义：

- `requestedContextSize`：上层请求的 ctx。
- `plannedContextSize`：libs/JJML 规划并用于创建 context 的 ctx。
- `promptTokenBudget`：`plannedContextSize - promptMarginTokens`。
- `memoryContextSize`：按当前设备可用显存、KV cache 成本和安全余量估算的 ctx 上限。
- `trainingContextSize`：模型元数据报告，仅作为信息，不由 libs 隐式当作硬上限。
- `reliable=false`：底层缺少完整显存或 KV 估算事实，上层不应把结果当作安全规划结论。

## 生成预算语义

修正并明确 `maxTokens` 语义：

- `maxTokens > 0`：调用方指定业务 completion 上限，但 libs 会按实际 ctx 剩余空间裁剪，避免越界。
- `maxTokens == 0`：调用方不指定业务输出上限；生成只受实际 ctx 剩余空间和 `promptMarginTokens` 约束。
- `promptMarginTokens` 只用于避免 prompt/生成贴到 ctx 物理边界，不表示业务输出保留。
- 当 prompt 已经占满上下文预算时，completion 预算为 0，本次请求正常结束并返回已知 usage，不进入无界生成。

## Gemma 分体 MTP

新增 Gemma 等分体 MTP draft 模型的显式加载路径：

- `JavaLlamaServer.Builder.mtpDraftModel(String path)`
- `ServerConfig.mtpDraftModelPath`

设计语义：

- 上层传入 draft 模型路径时，libs 加载外部分体 MTP draft 模型。
- 上层不传路径时，libs 不加载外部 MTP draft 模型。
- 已移除 MTP draft 自动发现逻辑，避免 libs 根据文件名或目录结构做隐式决策。
- 请求级是否使用 MTP 仍由 `InferenceOptions.mtpEnabled(...)` 控制。
- `InferenceOptions.mtpDraftMax(...)` 可覆盖本次请求的 draft max；不设置时使用校准推荐值。
- 未校准时默认 `draftMax=1`，避免首次启动时过于激进。
- libs 会自动缓存成功校准或运行期采样得到的推荐 `draftMax`，默认写入运行目录下的 `config/Tianshu/libs/mtp`；下次加载相同 target / draft / GPU 配置时自动使用缓存值，不要求上层回填。

运行能力报告新增/调整：

- `LlmRuntimeCapabilities.ready()`：当前模型服务是否已可用。
- `supportsThinking()`：当前已加载模型 / chat template 是否支持 thinking 控制。
- `LlmRuntimeCapabilities.supportsMtp()`：当前运行环境是否可用 MTP。
- `supportsEmbeddedMtp()`：主模型是否内置 MTP 能力。
- `externalMtpAvailable()`：是否已显式加载外部分体 MTP draft 模型。
- `mtpLayerCount()`：当前可报告的 MTP layer 数。

## Thinking / COT 结构化输出

新增请求级 COT 捕获开关：

- `InferenceOptions.captureThinkingContent(boolean)`
- `InferenceOptions.isCaptureThinkingContent()`

返回结构更新：

- `LlmGenerationResult(String text, LlmTokenUsage usage, String thinkingContent)`
- `LlmStreamFinish(StreamFinishType type, LlmTokenUsage usage, Throwable error, String thinkingContent)`

非流式语义：

- `LlmGenerationResult.text()` 只包含正式正文。
- `LlmGenerationResult.thinkingContent()` 在 `captureThinkingContent(true)` 时返回识别出的 thinking/COT 内容。
- `captureThinkingContent(false)` 时，libs 仍会识别并移除正文中的 thinking 包裹内容，但不保存 COT。

流式语义：

- `onToken` 只接收正式正文 token。
- `onThinking` 接收识别出的 thinking/COT token。
- `LlmStreamFinish.thinkingContent()` 返回本次流式请求的 thinking 汇总。
- TASK 被 CHAT 暂停并冷恢复时，已生成的正文和 thinking 内容都会随任务状态保留，不会串流到错误回调。

识别范围：

- 支持常见 `<think>...</think>`、`<reasoning>...</reasoning>` 等包裹。
- 支持 Gemma 观察到的 channel 形式，如 `<|channel>thought`、`<|channel>analysis`、`<|channel>final`、`<channel|>thought`、`<channel|>analysis`、`<channel|>final`。
- 支持 Gemma 输出中的裸 `<channel|>` 作为 reasoning 区段结束标记，避免其泄露到正文。

## API 清理

本次对比 staged diff，明确移除或不纳入以下旧入口/候选能力，避免过度设计或语义重复：

- `countEmbeddingTokens`
- `embedWithUsage`
- runtime capability 中的 tokenizer id / model id 暴露
- MTP draft 自动发现
- `outputReserve`
- `includeThinkingContent`
- `taskSuspendOnChat` 请求/配置入口；本次已从配置与调度判断中移除

其中：

- embedding token 数不作为本次 libs 接口能力提供。
- 上层已经掌握模型名称，libs 不额外传递模型 id。
- tokenizer 只作为 `countChatPromptTokens(...)` 的底层事实，不进入 runtime capability。
- 当前版本固定为 CHAT 可暂停 TASK；后续 task/chat 并行推理策略另行设计。

## 迁移提示

- 上层加载大 ctx 前，应先调用 `dryRunContextBudget()`，再把 `plannedContextSize` 显式写入 `contextSize(...)`。
- Gemma 分体 MTP 由上层显式传入 `.mtpDraftModel(path)` 控制；不传则不加载。
- 需要 COT 时，上层使用 `InferenceOptions.builder().captureThinkingContent(true).build()`，并读取 `thinkingContent()` 或注册 `onThinking`。
- 旧的纯字符串 `chat/task/chatStream/taskStream` 仍只返回正式正文。
